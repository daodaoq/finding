# 发布动态与找搭子功能审查报告

## 1. 审查范围

本次审查覆盖以下功能链路：

- 发布动态、编辑动态、删除动态
- 动态图片上传与保存
- 动态详情、评论、回复、评论点赞和删除
- 找搭子活动创建、编辑、取消和停止报名
- 找搭子活动列表、搜索、详情和筛选
- 报名、退出、审核申请、候补和名额计数
- 审核、拉黑、权限和活动地点脱敏

本报告只记录审查结果，不包含代码修改。

## 2. 总体结论

发布和找搭子主流程已经形成，且已有敏感词审核、用户写入限制、活动名额原子更新、候补机制、匿名活动和拉黑联动等基础能力。

但目前仍有几项必须优先处理的问题：

1. 找搭子时间存在明显的本地时间/UTC转换风险。
2. 动态编辑缺少写入权限检查，可能绕过禁言限制。
3. 评论相关接口没有验证评论和动态的归属关系。
4. 评论接口没有统一执行动态审核和可见性判断。
5. 活动详情没有复用列表中的拉黑过滤。
6. 动态图片缺少后端数量、来源和格式约束。

建议先修复 P0/P1 项，再补齐 P2 数据质量问题和并发回归测试。

## 3. 问题清单

### P0/P1：必须优先修复

#### 3.1 找搭子活动时间存在时区转换错误

- **位置**：`finding-web/src/pages/CreateMate/index.tsx:46`
- **现状**：表单使用 `datetime-local`，提交时调用 `new Date(activityTime).toISOString()`；后端 `MateCreateDTO.activityTime` 使用无时区的 `LocalDateTime`。
- **影响**：
  - 中国时区用户选择 18:00，可能被转换为 10:00 保存。
  - 如果后端没有自定义 `LocalDateTime` 反序列化，带 `Z` 的字符串可能直接返回参数解析错误。
  - 编辑活动时又把服务端时间转回本地输入框，可能出现二次偏移。
- **建议**：
  - 方案 A：前端提交本地字符串 `yyyy-MM-ddTHH:mm:ss`，后端继续使用 `LocalDateTime`。
  - 方案 B：前后端统一使用 `OffsetDateTime` 或带时区的时间戳，并明确存储时区。
  - 增加创建、编辑、详情展示的时区一致性测试。
- **验收标准**：用户在中国时区选择 18:00，保存、详情、编辑回显仍然都是 18:00。

#### 3.2 动态编辑没有执行写入权限检查

- **位置**：`finding-server/finding-module-post/src/main/java/com/finding/post/service/impl/PostServiceImpl.java:165`
- **现状**：`createPost` 调用 `userWriteGuard.checkWritable(userId)`，`updatePost` 没有调用。
- **影响**：被禁言、封禁或限制发言的用户仍可能编辑已有动态；这会绕过平台的内容写入策略。
- **建议**：在 `updatePost` 开头补充 `userWriteGuard.checkWritable(userId)`，并为禁言用户编辑场景增加服务层和控制器集成测试。
- **验收标准**：不可写用户创建和编辑动态均被拒绝；正常用户仍可编辑自己的动态。

#### 3.3 评论点赞和删除没有验证评论所属动态

- **位置**：
  - `finding-server/finding-module-post/src/main/java/com/finding/post/controller/PostController.java:83-95`
  - `finding-server/finding-module-post/src/main/java/com/finding/post/service/impl/PostServiceImpl.java:330-373`
- **现状**：控制器接收了路径中的 `postId`，但服务层只按 `commentId` 查询和操作。
- **影响**：调用者可以把某动态的评论 ID 放到另一个动态的 URL 下执行操作，接口路径与实际资源不一致；删除操作还会造成跨动态资源操作。
- **建议**：服务层查询评论时同时限定 `commentId` 和 `postId`；评论不存在或不属于该动态时返回统一的资源不存在错误。
- **验收标准**：跨动态评论 ID 的点赞、删除请求全部失败；正确动态下的操作正常。

#### 3.4 回复评论没有校验父评论归属

- **位置**：`finding-server/finding-module-post/src/main/java/com/finding/post/service/impl/PostServiceImpl.java:249-274`
- **现状**：`parentId` 直接写入，没有确认父评论属于当前动态、没有被删除且仍可回复。
- **影响**：可能形成跨动态回复树；通知会发送给错误的评论作者；前端评论结构可能无法正确展示。
- **建议**：查询父评论并校验：
  - `parent.postId == postId`
  - 父评论状态正常
  - 动态本身可见且未删除
- **验收标准**：跨动态 parentId、已删除 parentId、不存在 parentId 均被拒绝。

#### 3.5 评论列表没有统一执行动态可见性检查

- **位置**：`finding-server/finding-module-post/src/main/java/com/finding/post/service/impl/PostServiceImpl.java:233-245`
- **现状**：评论接口直接按 `postId` 查询评论，没有复用动态详情中的状态和审核判断。
- **影响**：知道动态 ID 的用户可能直接读取待审核、审核拒绝或已删除动态的评论数据。
- **建议**：查询评论前复用统一的动态可见性方法，至少校验动态存在、未删除、审核通过；作者本人是否可查看待审内容要明确规定。
- **验收标准**：普通用户无法通过评论接口读取不可见动态的数据。

### P1：业务和隐私风险

#### 3.6 搭子详情没有复用拉黑过滤

- **位置**：`finding-server/finding-module-mate/src/main/java/com/finding/mate/service/impl/MateServiceImpl.java:149-159`
- **现状**：列表和搜索通过 `applyPublicFilter` 排除拉黑用户，但详情接口只按活动 ID 查询。
- **影响**：被拉黑用户仍可通过历史链接或猜测 ID 查看活动标题、描述、活动时间等信息。虽然报名接口会再次拦截，但可见性策略不一致。
- **建议**：详情接口在返回前检查双方拉黑关系；被拉黑时返回统一的 `MATE_NOT_FOUND`，避免泄露资源存在性。
- **验收标准**：拉黑双方无法通过直接活动链接查看对方的活动。

#### 3.7 活动地点脱敏规则没有集中管理

- **位置**：
  - `finding-server/finding-module-mate/src/main/java/com/finding/mate/service/impl/MateServiceImpl.java:107-129`
  - `finding-server/finding-module-mate/src/main/java/com/finding/mate/service/impl/MateServiceImpl.java:538-555`
- **现状**：主详情 VO 会根据发起人/已通过成员决定是否返回地点，但搜索结果、申请记录和其他管理出口各自组装地点字段。
- **影响**：后续新增接口时容易遗漏脱敏；匿名活动和未通过申请可能出现地点泄露。
- **建议**：抽取统一的 `resolveVisibleLocation` 或权限策略，并对所有 VO、Map 返回出口进行审计。
- **验收标准**：未报名、待审核、被拒绝和匿名活动用户只能看到模糊地点；发起人和已通过成员看到精确地点。

#### 3.8 找搭子列表页未登录时直接调用报名接口

- **位置**：`finding-web/src/pages/Mate/index.tsx:46-53`
- **现状**：详情页使用 `useRequireLogin`，列表页点击报名后直接调用 `mateApi.join`。
- **影响**：未登录用户点击报名只能收到接口错误，无法进入统一登录流程，体验和权限处理不一致。
- **建议**：列表页复用 `useRequireLogin`，登录成功后再执行报名回调。
- **验收标准**：未登录点击报名打开登录弹窗；登录成功后继续原操作。

#### 3.9 离开活动缺少活动状态和参与状态校验

- **位置**：`finding-server/finding-module-mate/src/main/java/com/finding/mate/service/impl/MateServiceImpl.java:403-415`
- **现状**：服务层找到参与记录后直接处理；没有先确认活动仍处于有效状态，也没有使用状态条件保护更新。
- **影响**：对已取消、已结束活动重复调用离开接口，可能继续减少 `current_participants`，造成统计短暂不一致。
- **建议**：
  - 校验活动状态为 ACTIVE 且未过期。
  - 仅允许 ACCEPTED 状态执行释放名额逻辑。
  - 使用带原状态条件的原子更新，避免重复请求重复扣减。
- **验收标准**：重复离开、活动取消后离开、已拒绝申请离开都不会修改名额。

### P2：数据质量和可维护性问题

#### 3.10 动态图片字段缺少后端约束

- **位置**：`finding-server/finding-module-post/src/main/java/com/finding/post/service/impl/PostServiceImpl.java:153-154`
- **现状**：前端限制最多 9 张图片，但后端只接收 `List<String>` 并直接保存，没有限制数量、单项长度、协议和来源。
- **影响**：调用 API 可以绕过前端提交大量 URL 或外部资源；可能造成数据库膨胀、页面加载异常和外部追踪风险。
- **建议**：后端限制图片数量和 URL 长度，仅允许受信任上传接口返回的地址，并校验上传记录归属当前用户。
- **验收标准**：超出数量、超长 URL、非受信任域名和非法协议均被拒绝。

#### 3.11 图片使用逗号拼接存储会损坏特殊 URL

- **位置**：`finding-server/finding-module-post/src/main/java/com/finding/post/service/impl/PostServiceImpl.java:153、174、438`
- **现状**：写入使用 `String.join(",", urls)`，读取使用 `split(",")`。
- **影响**：URL 或查询参数包含逗号时会被拆成多个错误地址；图片无法正常回显。
- **建议**：短期改为 JSON 数组序列化；长期改为独立的 `post_image` 表，记录顺序、文件地址和上传者。
- **验收标准**：包含逗号、中文编码参数和多个查询参数的图片地址都能完整保存和回显。

#### 3.12 动态详情评论数包含已删除评论

- **位置**：`finding-server/finding-module-post/src/main/java/com/finding/post/service/impl/PostServiceImpl.java:133-135`
- **现状**：动态列表同步评论数时过滤 `status = 0`，详情接口统计评论数时没有状态过滤。
- **影响**：列表页和详情页的评论数量不一致；删除评论后计数仍可能偏大。
- **建议**：详情统计与列表统计统一使用 `status = 0`，并补充删除评论后的回归测试。

#### 3.13 动态详情浏览量可被低成本刷高

- **位置**：`finding-server/finding-module-post/src/main/java/com/finding/post/service/impl/PostServiceImpl.java:136-138`
- **现状**：每次详情请求都会直接增加一次浏览量，没有用户、设备或时间窗口去重。
- **影响**：热门排序和运营数据容易被刷量影响；高频请求会对数据库产生额外写压力。
- **建议**：使用 Redis 按用户或访客会话做短期去重，或将浏览事件异步化后批量写入。
- **验收标准**：同一用户在短时间内重复刷新不会无限增加浏览量；数据写入压力可控。

## 4. 现有实现中值得保留的机制

- 动态和搭子内容均经过 XSS 清洗及敏感词分类。
- 搭子创建和报名受到认证状态限制。
- 搭子报名存在待审核、已通过、拒绝、退出和候补状态。
- 通过申请时使用名额条件更新，具备一定的并发防超卖保护。
- 拉黑事件会使相关搭子关系失效。
- 匿名活动会隐藏发起人 ID，并对集合地点进行脱敏。
- 已有服务层单测覆盖部分敏感词审核、候补和并发名额场景。

## 5. 测试补充计划

### 时间与表单

- 中国时区创建活动后时间不偏移。
- 编辑活动后时间回显不偏移。
- 过期时间、当前时间后 30 分钟以内的时间均被正确拒绝。

### 动态权限与可见性

- 禁言用户无法创建和编辑动态。
- 普通用户无法读取待审、拒绝或已删除动态的评论。
- 动态删除后评论、评论点赞和回复接口均返回正确错误。

### 评论资源归属

- 跨动态 `commentId` 点赞失败。
- 跨动态 `commentId` 删除失败。
- 跨动态 `parentId` 回复失败。
- 已删除父评论不能继续创建回复。

### 图片

- 图片数量上限、单项 URL 长度和协议校验。
- 非上传接口返回的 URL 被拒绝。
- 包含逗号的 URL 可以完整保存和回显。

### 搭子并发与状态

- 多人同时通过申请时不会超过名额上限。
- 满员后候补按申请时间顺序晋升。
- 重复通过、重复拒绝、重复离开不会重复修改名额。
- 活动取消、关闭、过期后不能新增报名或修改参与关系。
- 拉黑后不能通过详情链接读取或报名。

## 6. 建议修复顺序

1. 统一活动时间的时区协议。
2. 修复动态编辑写权限检查。
3. 修复评论、回复的资源归属校验。
4. 给评论接口补充动态可见性判断。
5. 统一搭子详情拉黑和地点脱敏策略。
6. 修复搭子列表页未登录报名流程。
7. 加固离开活动的状态和并发保护。
8. 增加图片后端校验并停止逗号拼接存储。
9. 统一评论数统计并增加浏览量限频。
10. 按本报告测试计划补齐自动化回归测试。
