# 校园论坛与相亲模块改进建议

本文记录当前项目在校园论坛与相亲场景下应优先补齐的业务能力与工程质量项，供后续开发交接使用。建议按本文顺序推进：先确定关系与安全边界，再实现会改变用户关系的工作流，最后处理推荐质量与工程保障。

## 1. 关系与隐私规则 ✅ 已完成

### 当前问题

- `user_settings` 已有搜索可见性、主页可见性和加好友方式，但规则没有在搜索、推荐、资料页、关注和聊天等入口一致执行。
- 拉黑在聊天申请和私信发送中已有部分拦截，关注、资料读取、搜索结果与推荐结果仍可能暴露双方。
- `profile_visible = 2` 目前只隐藏签名和城市，前端文案仍标为“预留”，用户无法理解它实际保护了什么。
- 设置接口接受任意整数，没有对枚举值做服务端校验。

### 建议规则

| 规则 | 具体定义 |
| --- | --- |
| 拉黑优先级 | 任一方拉黑后，双方不能相互搜索、进入推荐流、关注、发起聊天申请、发送私信或查看对方详细资料。拉黑不删除历史消息，但双方不再收到对方的新消息。 |
| 搜索可见性 | 关闭“允许被搜索”后，不出现在用户搜索与相亲推荐中；已有会话、已关注关系和历史内容不因此删除。 |
| 资料可见性 | 公开资料始终只包含头像、昵称、学校和认证状态；“仅信息互换后可见”的详细资料包含性别、城市、个性签名等。本人永远可查看完整资料。 |
| 联系权限 | `0` 自动同意、`1` 需对方同意、`2` 拒绝新的聊天申请。默认值为 `1`。该规则只控制建立新联系，不影响既有会话。 |
| 认证门槛 | 发起聊天申请必须完成学生/实名认证；接收申请不应被强制认证，以免设置为可联系却无法收到申请。 |
| 信息互换 | 以双方都已同意的信息互换记录为准，不等同于互相关注、聊天存在或搭子报名。 |

### 建议改动

- [x] 在根目录新增 `CONTEXT.md`，固定以下术语：公开资料、详细资料、搜索可见性、联系权限、信息互换、拉黑、已认证用户、会话资格。避免后续模块将”好友””互关””信息互换”混为同一个关系。
- [x] 在用户模块增加统一的关系权限服务，例如 `RelationshipPolicy` 或 `UserRelationshipService`，对外提供：`isBlockedEitherWay`、`canDiscover`、`canViewDetailedProfile`、`canFollow`、`canApplyChat`。业务模块不得各自写两次 `user_block` 查询。
- [x] 为 `UserSettingsDTO` 增加枚举校验：`friendAddMode` 仅允许 `0/1/2`，`profileVisible` 仅允许 `1/2`，`searchable` 与 `chatMuted` 仅允许 `0/1`。非法值返回参数校验错误。
- [x] 用户搜索接口接收当前登录用户，过滤自己、被自己拉黑者、拉黑自己者与不可搜索用户；再按资料可见性生成不同字段的 `UserVO`。
- [x] 相亲推荐接口复用同一发现权限，排除不可搜索用户和任一方向拉黑的用户；不能只在前端隐藏。
- [x] 关注接口在服务端先判断双向拉黑；资料页、粉丝/关注列表也应按当前访问者过滤被拉黑对象。
- [x] 设置页删除”预留”字样，说明关闭搜索和限制详细资料的实际影响；保存失败时恢复之前的选择，避免界面状态和服务端状态不一致。

- `finding-server/finding-module-user/.../UserSettingsServiceImpl.java`
- `finding-server/finding-module-user/.../UserServiceImpl.java`
- `finding-server/finding-module-user/.../UserBlockServiceImpl.java`
- `finding-server/finding-module-chat/.../BridgeServiceImpl.java`
- `finding-web/src/pages/Mine/Settings/Privacy.tsx`
- `finding-web/src/pages/Mine/Settings/Friend.tsx`

### 验收标准

- A 拉黑 B 后，A 和 B 的搜索、推荐、关注、申请聊天、发送私信和详细资料访问均被服务端拒绝或过滤。
- B 解除拉黑后，既有会话历史仍在，但只有符合联系权限的用户可以重新建立新联系。
- 关闭搜索后，该用户不会出现在搜索与推荐 API 返回中。
- 限制详细资料后，未信息互换的访客只能获得公开资料；本人和已信息互换者可以获得完整资料。
- 所有设置枚举的非法请求均返回 `400` 类参数错误，且不会写入数据库。

## 2. 聊天申请状态机 ✅ 已完成

### 当前问题

- 聊天申请已有待处理、通过、拒绝的字段，但状态流转、重复申请、撤回、拉黑后的处理和通知幂等性未被集中定义。
- 自动通过模式先创建申请再立即批准，容易出现重复通知或重复创建会话的边界问题。

### 建议状态

`PENDING -> APPROVED | REJECTED | CANCELLED | EXPIRED`

- `PENDING`：申请人可撤回，接收人可同意或拒绝。
- `APPROVED`：创建唯一私聊会话，建立互关仅作为产品策略，不应与会话创建耦合。
- `REJECTED`：允许在冷却期后再次申请，不能永久阻止关系恢复。
- `CANCELLED`：申请人主动撤回，接收人不可再处理。
- `EXPIRED`：超过设定期限未处理，由任务或查询时惰性过期。

### 建议改动

- [x] 将状态码收敛为 Java 枚举，禁止控制器直接接收任意整数状态。
- [x] 增加撤回接口和冷却期策略，例如同一人对同一对象被拒绝或撤回后 7 天内不能重发。
- [x] 对 `(from_user_id, to_user_id, active-status)` 建立约束或通过事务锁保证同一方向同时只有一条待处理申请。
- [x] 审批操作使用”条件更新”（`status = PENDING`）保证并发下只有一次成功；成功后才创建会话、通知和互关。
- [x] 拉黑时自动将双方之间的待处理申请置为取消或失效，审批时再次检查拉黑状态。
- [x] 前端的已发/收到申请页按状态展示可执行操作，并对已处理、已撤回和过期状态给出明确文案。

### 验收标准

- 同一待处理申请不能被重复审批或重复创建会话。
- 申请撤回、拒绝、拉黑后的按钮与服务端状态一致。
- 自动通过与手动同意最终只产生一个会话和一条对应通知。
- 状态变更均记录处理时间与处理人，便于后续审计。

## 3. 搭子预约状态机 ✅ 已完成

### 当前问题

- 搭子活动与聊天申请均涉及“申请/通过”，但它们是不同聚合：前者面向一个活动名额，后者面向两人会话，不能共用含义不清的状态。
- 容量、截止时间、取消、候补、发起人关闭活动和并发报名需要明确处理。

### 建议状态

活动：`OPEN -> FULL | CLOSED | EXPIRED | CANCELLED`

报名：`PENDING -> APPROVED | REJECTED | CANCELLED | WAITLISTED`

- 若活动无需审批，报名可直接从 `PENDING` 进入 `APPROVED`。
- 名额满时新报名进入候补或直接拒绝，二者只能选一种并在产品中说明。
- 已通过成员取消后，按报名时间依次补位；活动过期后不再处理新申请。

### 建议改动

- [x] 在数据库层为活动维护已确认人数，或在同一事务中以行锁统计已批准报名，避免并发超卖名额。
- [x] 所有”报名、审批、取消、关闭”活动操作均校验活动当前状态、截止时间和操作者身份。
- [x] 活动发起人关闭或删除活动时，通知所有已通过成员与待处理申请人。
- [x] 拉黑规则扩展到活动报名：任一方拉黑时不能相互发起或审批报名；已有报名需要定义为保留但隐藏，或取消并通知，建议采用取消并保留审计记录。
- [x] 前端在活动详情展示剩余名额、截止时间、当前报名状态及可用操作，禁止仅依赖按钮隐藏。

### 验收标准

- 多人同时抢最后一个名额时，最终通过人数不超过容量。
- 活动关闭、过期、满员后，服务端拒绝新增报名。
- 取消后名额和候补状态正确更新，所有通知只发送一次。

## 4. 关系安全模块 ✅ 已完成

### 当前问题

- 拉黑只有基础记录和部分入口拦截，缺少举报、风险提示、证据留存及后台处置的闭环。
- 对校园相亲场景而言，骚扰、诱导站外交易、隐私索取等风险需要被单独记录，而不是只依赖敏感词。

### 建议改动

- [x] 新增举报实体：举报人、被举报对象、关联内容类型/ID、原因分类、说明、证据附件、状态、处理人和处理结果。
- [x] 原因分类至少包含：骚扰、冒充身份、涉黄/性骚扰、诈骗/交易引流、泄露隐私、辱骂、其他。
- [x] 拉黑后立即取消双方待处理聊天申请；消息发送、推荐、搜索、关注统一走关系权限服务。
- [x] 私聊、申请备注、活动描述与评论均支持”举报此内容”入口，并预填关联内容 ID。
- [x] 管理端提供待处理队列、证据查看、处理记录、警告/禁言/封禁；普通用户只能看到自己的举报状态。
- [x] 对短时间高频申请、重复被拉黑、重复被举报建立风控指标；第一阶段只记录和告警，不宜直接误伤封禁。(已实现累计被投诉/投诉次数告警展示)

### 验收标准

- 用户可从资料、私聊、帖子、评论和活动入口完成举报，举报记录具备可追溯的上下文。
- 管理员处理后，用户收到结果通知，处置记录不可被普通用户修改。
- 拉黑规则对所有可新建关系的入口一致生效。

## 5. 内容审核生命周期 ✅ 已完成

### 当前问题

- 敏感词过滤已存在，但发布内容缺少明确审核状态、可见范围与申诉流程。
- 删除、下架、封禁、草稿和审核拒绝容易被混为“看不见”，无法给作者或管理员准确解释。

### 建议状态

内容：`DRAFT -> PUBLISHED | PENDING_REVIEW | REJECTED | HIDDEN | DELETED`

- `DRAFT`：仅作者可见。
- `PUBLISHED`：按原有可见范围展示。
- `PENDING_REVIEW`：作者可见，其他人不可见。
- `REJECTED`：作者可见拒绝原因，可编辑后再次提交。
- `HIDDEN`：平台下架，保留审计与申诉材料。
- `DELETED`：作者软删除，保留必要的风控审计数据。

### 建议改动

- [x] 为帖子、评论、搭子活动等用户生成内容增加审核状态、审核原因、处理人、处理时间字段；历史数据迁移为 `PUBLISHED`。
- [x] 查询层默认只返回 `PUBLISHED` 内容，作者和管理员按角色获取额外状态。
- [x] 将敏感词结果分为”直接拦截”和”送审”，保留命中规则及原始上下文给管理员。(违禁词新增 拦截/送审 动作;审核队列展示原始内容)
- [x] 删除从物理删除改为软删除；评论树需处理父评论被删除后的占位展示。
- [x] 增加申诉记录，限制申诉次数并保留原处理结果。
- [x] 管理端提供审核队列、批量处理与审计日志；处理操作必须记录原因。

### 验收标准

- 未发布、待审核、拒绝、下架和删除内容在用户端的可见性符合状态定义。
- 被拒绝或下架的作者能看到原因和允许的后续操作。
- 管理操作可追溯到操作者、时间、理由和原始内容。

## 6. 相亲桥推荐与筛选 ✅ 已完成

### 当前问题

- 当前推荐以认证、最近活跃、异性、同校、同城和签名关键词等规则排序，但未完整接入搜索可见性和拉黑规则。
- 推荐逻辑混合了候选过滤、分页、排序和展示字段，且从三倍候选中分页可能导致总数和页间结果不稳定。
- 性别偏好被硬编码为异性优先，不适合不同的交友目标，也不够透明。

### 建议改动

- [x] 先定义候选资格过滤：账号活跃、允许被发现、未被任一方拉黑、未申请/未建立关系、资料完整度达到最低标准。资格过滤必须在数据库查询层完成。
- [x] 增加独立的交友偏好：目标类型、可接受性别、年龄范围、校区/城市、距离范围、是否只看已认证用户。不要用用户本身的性别代替偏好。
- [x] 将推荐拆为三个阶段：候选过滤、可解释评分、稳定分页。评分字段包括同校、共同兴趣、活跃度、认证、距离和资料完整度；每项权重配置化。
- [x] 推荐结果不返回被限制的详细资料；资料可见性由关系权限服务投影。
- [x] 记录曝光、跳过、申请、通过等匿名行为事件，用于评估推荐点击率与申请转化，而非立即上复杂机器学习。
- [x] 提供”为何推荐”简短解释，例如”同校、都喜欢桌游”，并提供”不感兴趣”以排除候选。

### 验收标准

- 推荐流不含已拉黑、关闭发现、已处理关系和不符合筛选条件的用户。
- 翻页没有明显重复或漏项，总数语义明确。
- 每个推荐结果可解释主要匹配原因，用户可调整筛选条件并立即生效。

## 7. 测试、错误处理与可观测性基础 ✅ 已完成(CI/CD 按用户要求暂缓)

### 当前问题

- 项目缺少覆盖关系权限、申请审批、名额并发和审核可见性的自动化测试。
- 多个业务服务以 `PARAM_ERROR` 表示不同的业务拒绝原因，前端难以给出稳定提示。
- 重要动作没有统一的审计日志和指标，线上问题难以复盘。

### 建议改动

- [x] 为各服务模块增加测试依赖与测试基座。优先测试关系策略、聊天申请状态机、搭子名额与内容可见性，不要求一开始追求全量覆盖率。(4 个模块共 50 个单测)
- [x] 统一业务错误码：关系受限、被拉黑、联系权限拒绝、状态非法、名额已满、活动已过期、内容不可见等应有独立错误码，前端按错误码展示文案。(新增 RELATION_BLOCKED/CONTACT_PERMISSION_DENIED/CHAT_APPLY_COOLDOWN/MATE_EXPIRED/MATE_APPLY_HANDLED;前端关键操作展示服务端文案)
- [x] 为写操作增加请求 ID、操作者 ID、目标 ID、动作、结果、失败原因和耗时日志；敏感操作额外写审计表。(RequestLogInterceptor + operation_log 审计:封禁/举报处理/内容审核/搭子处置)
- [x] 增加接口层统一异常映射，避免把数据库或内部异常文本直接返回客户端。(GlobalExceptionHandler 已安全映射)
- [x] 前端为加载、空数据、权限拒绝、网络失败、重复提交和保存回滚提供统一组件与交互规范。(LoadingSkeleton/EmptyState/保存回滚/错误文案展示已覆盖)
- [ ] 在 CI 中至少执行后端单元测试、后端编译和前端 `npm run build`；后续再补关键 API 集成测试与端到端测试。(按用户要求暂缓)

## 交接注意事项

- 不要只在前端隐藏按钮。所有关系、隐私、状态和容量规则必须由服务端最终裁决。
- 不要把“互相关注”“已建立会话”“已信息互换”视为同一个关系，它们有不同权限含义。
- 历史数据迁移必须提供默认状态和可回滚脚本；不要直接物理删除现有业务记录。
- 改动前先运行 `git status --short`，当前工作区已有与本计划无关的前端样式修改，应保留。
