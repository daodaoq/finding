# 聊天功能审查与修改建议

## 1. 审查范围

本次审查覆盖以下链路：

- 聊天申请与会话创建
- 私聊消息发送、历史记录、已读、撤回、搜索和单侧清空
- WebSocket 实时连接与 RabbitMQ 异步推送
- 拉黑、免打扰、举报和信息互换
- 前端消息列表、乐观发送、未读数与断线重连
- 数据库约束与现有自动化测试

主要涉及代码：

- `finding-server/finding-module-chat/src/main/java/com/finding/chat/controller/ChatController.java`
- `finding-server/finding-module-chat/src/main/java/com/finding/chat/service/impl/ChatServiceImpl.java`
- `finding-server/finding-module-chat/src/main/java/com/finding/chat/service/impl/BridgeServiceImpl.java`
- `finding-server/finding-module-chat/src/main/java/com/finding/chat/event/MsgSendConsumer.java`
- `finding-server/finding-framework/src/main/java/com/finding/framework/websocket/WebSocketServer.java`
- `finding-web/src/pages/Chat/index.tsx`
- `finding-web/src/hooks/useWebSocket.ts`
- `finding-server/finding-app/src/main/resources/schema.sql`

## 2. 总体结论

当前聊天功能不是空壳，已经具备会话列表、私聊、图片、消息历史、已读、撤回、搜索、单侧清空、会话设置、拉黑、举报、信息互换、WebSocket 和 RabbitMQ 推送等基础能力。

但现状仍不适合直接上线，存在三项高危问题：

1. 非会话成员可以通过猜测 `roomId` 读取其他人的私聊历史。
2. WebSocket 客户端消息会被服务器直接转发，绕过落库、认证、拉黑、联系权限、敏感词和消息类型校验。
3. 已认证用户可以直接调用创建会话或发送消息接口，绕过聊天申请和对方的“需验证/不允许申请”设置。

除安全问题外，历史消息分页、免打扰、发送回执、数据库唯一约束和 MQ 可靠性也有确定缺陷。建议按本文优先级修复。

## 3. P0：必须立即修复的安全问题

### 3.1 历史消息接口存在越权读取 ✅ 已完成

#### 现状

`ChatServiceImpl.getMessageHistory` 根据 `roomId` 查询 `room_friend`，但没有确认当前用户等于 `uid1` 或 `uid2`。

当前判断逻辑相当于：

```java
if (rf != null) {
    if (rf.getUid1().equals(userId)) {
        // uid1 视角
    } else {
        // 所有不是 uid1 的用户都被当成 uid2
    }
}
```

因此，任意已登录用户只要获得或枚举到一个有效 `roomId`，就可能读取该房间的全部私聊内容。即使 `room_friend` 不存在，代码仍会直接按 `roomId` 查询消息。

#### 影响

- 私聊隐私泄露。
- 图片 URL、信息互换内容和历史对话可能被第三方获取。
- 属于典型的对象级权限校验缺失，不能依靠前端路由隐藏解决。

#### 修改建议

1. 新增统一方法 `requireRoomMember(userId, roomId)`，查询 `room_friend` 并确认当前用户为 `uid1` 或 `uid2`。
2. `getMessageHistory`、`markConversationRead`、`getConversationSettings`、`updateConversationSettings`、`searchMessages`、`clearMessages` 和基于房间的举报全部调用该方法。
3. 非成员统一返回 `FORBIDDEN`，不要返回“房间不存在”，避免接口间权限语义不一致。
4. 不要以 `contact` 记录单独作为成员身份依据；`contact` 是会话列表投影，成员关系应以 `room_friend` 为准。

#### 验收标准

- 第三名用户请求其他两人的 `roomId` 时，历史、已读、设置、搜索、清空和举报接口均返回无权限。
- `roomId` 不存在时返回会话不存在；存在但非成员时返回无权限。
- 增加控制器或服务集成测试覆盖成员、非成员和不存在房间三种情况。

### 3.2 WebSocket 存在绕过全部业务规则的直接转发通道 ✅ 已完成

#### 现状

`WebSocketServer.handleTextMessage` 收到 `type = chat` 后，仅用 JWT 覆盖 `fromUserId`，随后直接执行：

```java
sendToUser(wsMsg.getToUserId(), wsMsg);
```

它没有调用 `ChatService.sendMessage`，也没有执行以下规则：

- 学生/实名认证校验
- 是否已经建立合法会话
- 对方联系权限
- 双向拉黑
- 敏感词过滤和 XSS 清洗
- 消息长度与消息类型校验
- 消息落库
- 已读数、会话活跃时间和最后消息更新

恶意客户端可以通过 WebSocket 向任意在线用户发送一条“看起来真实但刷新后消失”的消息。

#### 影响

- 可绕过拉黑和聊天申请进行骚扰。
- 接收端可能显示数据库中不存在的消息，无法正常举报、撤回或审计。
- 可伪造任意 `messageId`、`conversationId`、`messageType` 和内容。
- 服务端注释声称支持 WebSocket 发送，但当前实现没有达到业务安全要求。

#### 修改建议

推荐只保留一种写入通道：

1. 客户端通过 REST 或受控命令发送消息。
2. 服务端完成权限校验、内容处理和事务落库。
3. 事务提交后通过 MQ 和 WebSocket推送已落库的标准消息 DTO。
4. WebSocket 仅用于服务端向客户端推送、心跳和已读/输入状态等轻量事件，不直接接受聊天内容写入。

如果必须支持 WebSocket 发消息，则 `handleTextMessage` 只能把命令交给 `ChatService`，不得直接转发，并且需要向发送端返回成功或失败回执。

同时将 WebSocket 允许来源从 `*` 改为配置化的可信前端域名列表。

#### 验收标准

- 客户端自行发送 WebSocket `type = chat` 不会直接抵达接收者。
- 所有可见聊天消息都能在数据库中找到唯一记录。
- 被拉黑、未认证或无会话资格的用户无法通过 REST 或 WebSocket 发送消息。
- 接收端只接受包含真实服务端消息 ID 的推送。

### 3.3 创建会话和发送消息绕过聊天申请 ✅ 已完成

#### 现状

`POST /api/v1/chat/conversations?targetUserId=...` 可直接调用 `getOrCreateConversation`。该方法仅检查不能和自己聊天，以及新建房间时双方是否拉黑，没有检查聊天申请是否已通过。

`POST /api/v1/chat/send` 同样会调用 `getOrCreateConversation`。因此已认证用户可以跳过鹊桥聊天申请，直接对任何未拉黑用户创建房间并发消息。

这会使 `friendAddMode` 的以下设置失效：

- `1`：需要对方同意
- `2`：不允许新的聊天申请

前端聊天页打开时还会主动调用创建会话接口，因此只要能构造聊天路由，就会创建一条会话。

#### 修改建议

1. 将“查找已有会话”和“批准申请后创建会话”拆成两个语义明确的方法。
2. 普通用户接口只允许获取已经存在且自己是成员的会话，不能随意创建。
3. 新会话只能由聊天申请批准流程创建；自动通过模式也必须先产生合法申请并在同一事务中批准。
4. `sendMessage` 只接受 `roomId + content`，先验证发送者为房间成员，再从房间关系中确定接收者，避免客户端自行指定任意 `toUserId`。
5. 如果产品允许互相关注用户直接私聊，需要把它定义成明确规则并由服务端检查，不能隐式放开全部已认证用户。

#### 验收标准

- 未申请或申请未通过时，无法创建会话和发送消息。
- 对方设置为“不允许申请”时，不能通过聊天接口绕开。
- 已批准申请只能创建一个唯一会话。
- 客户端不能通过篡改 `toUserId` 把消息发送到房间外用户。

## 4. P1：上线前必须修复的一致性问题

### 4.1 历史消息分页方向错误，50 条以上记录无法正常查看

#### 现状

后端初次查询使用 `orderByAsc(createdAt)`，固定查询第 1 页，因此返回最早的 50 条，而不是最新的 50 条。

前端上拉加载更早消息时，传入当前最小 ID；因为初次已经是最早的一批，再查询 `id < minId` 通常会得到空结果。用户无法正常到达后续较新的消息。

#### 修改建议

使用基于消息 ID 的游标分页：

1. 初次请求按 `id DESC` 查询最新 50 条。
2. 有 `beforeId` 时查询 `id < beforeId`，仍按 `id DESC` 限制 50 条。
3. 返回前在服务端或前端反转为时间正序展示。
4. `hasMore` 使用“多查一条”或明确的下一游标计算，不要混用页码总数语义。
5. 对 `size` 设置范围，例如 `1..100`。

#### 验收标准

- 120 条消息首次打开显示第 71 至 120 条。
- 连续两次上拉依次加载第 21 至 70 条、第 1 至 20 条。
- 页面内没有重复、遗漏或时间顺序颠倒。

### 4.2 私聊发送缺少服务端消息回执，临时消息无法可靠撤回

#### 现状

前端发送时用 `Date.now()` 作为临时消息 ID，REST 成功后没有用真实数据库 ID 替换。后端 `sendMessage` 只返回 `ConversationVO`，不会返回新消息。

发送者也不会收到自己的普通消息 WebSocket 推送，因此临时 ID 会一直存在到刷新页面。用户刚发送后点击撤回，前端会把临时 ID 当成数据库 ID，请求通常失败。

#### 修改建议

1. `sendMessage` 返回完整 `ChatMessageVO`，至少包含真实 `id`、`roomId`、发送者、接收者、内容类型和服务端时间。
2. 前端为每次发送生成 `clientMessageId`，成功后用返回记录替换临时消息。
3. 失败消息不要立即彻底删除，建议显示“发送失败”和“重试”。
4. 服务端以 `senderId + clientMessageId` 做幂等，避免弱网重试产生重复消息。
5. 同一账号其他设备也应收到自己发送成功的同步事件。

#### 验收标准

- 发送成功后页面消息 ID 与数据库 ID 一致。
- 新发送的消息可立即撤回和举报。
- 网络超时重试不会产生重复消息。

### 4.3 免打扰错误地阻止消息数据同步

#### 现状

`MsgSendConsumer` 在接收方开启免打扰时不发送 WebSocket 消息。

免打扰的合理语义应是关闭声音、系统通知或角标提醒强度，而不是停止聊天数据同步。当前实现会导致接收者正在聊天页面时收不到新消息，必须刷新才能看到。

#### 修改建议

1. 无论是否免打扰，都向在线客户端推送消息数据。
2. 推送中携带 `muted` 或客户端根据本地会话设置判断是否播放声音、震动和弹出通知。
3. 会话列表、当前聊天页和多设备同步不得受免打扰影响。

#### 验收标准

- 开启免打扰后，聊天页仍实时出现新消息。
- 不播放声音、不触发系统弹窗，但未读数与消息内容保持正确。

### 4.4 WebSocket 会重复连接，并且卸载后可能继续重连

#### 现状

`MainLayout` 已经建立全局 WebSocket，聊天页、群聊页和消息页又各自调用 `useWebSocket`，一个浏览器标签可能同时保持多个连接。

`useWebSocket` 在 `onclose` 中直接 `setTimeout(connect, 3000)`。组件卸载时主动关闭连接也会触发 `onclose`，但定时器没有保存和清理，可能在组件卸载后重新建立连接。认证失败时也会每 3 秒永久重连。

#### 修改建议

1. 建立单例 WebSocket Provider，由 `MainLayout` 维护唯一连接。
2. 页面通过事件订阅注册回调，不再各自创建连接。
3. 保存重连定时器，并在卸载、退出登录和 token 失效时取消。
4. 使用指数退避与随机抖动，例如 1、2、4、8、30 秒上限。
5. 区分主动关闭、认证失败和网络断开；认证失败应刷新 token 或停止重连。
6. 增加连接状态，以便界面显示“连接中/已断开”，恢复后补拉未读消息。

#### 验收标准

- 单个浏览器标签最多保持一个聊天 WebSocket。
- 路由切换不会产生后台遗留连接。
- 退出登录后不再重连；断网恢复后只重连一次。

### 4.5 `contact` 缺少唯一约束，存在重复会话列表记录风险

#### 现状

`contact` 表只有普通索引 `idx_uid_room(uid, room_id)`，没有唯一约束。`ensureContact` 和 MQ 消费者都采用“先查后插”，并发时可能为同一个用户和房间插入多条记录。

后续 `selectOne` 可能抛出多结果异常，会话列表也可能重复显示。

#### 修改建议

1. 将索引改为唯一索引 `UNIQUE KEY uk_uid_room(uid, room_id)`。
2. 迁移前先查重并保留每组最新或数据最完整的一条记录。
3. 创建联系记录使用幂等插入，捕获唯一键冲突后重新查询。
4. `room_friend.room_key` 已有唯一约束，但并发创建时应在冲突后查询已存在房间，而不是直接把请求作为失败返回。

#### 验收标准

- 并发创建同一会话时只产生一个 `room_friend` 和每人一条 `contact`。
- MQ 重复投递不会增加重复联系人记录。

### 4.6 消息落库和 MQ 发布之间存在可靠性缺口

#### 现状

消息事务提交后，代码在 `afterCommit` 中调用 RabbitMQ。若数据库提交成功但 RabbitMQ 不可用，消息已经落库，推送事件却可能永久丢失。

当前未看到生产者确认、失败重试、死信队列或本地消息表与补偿任务。此时接收者不会实时收到消息，会话活跃时间和最后消息也不会更新。

#### 修改建议

1. 推荐使用事务 Outbox：消息落库与待发布事件在同一数据库事务中写入。
2. 后台任务发布 Outbox，收到 broker confirm 后标记完成，失败按策略重试。
3. 为消费失败配置有限重试和死信队列，避免单条异常消息无限阻塞。
4. 消费者按消息 ID 幂等，重复消费只更新同一状态。
5. 增加消息发布失败、积压数量、死信数量和消费延迟监控。

#### 验收标准

- RabbitMQ 暂停期间发送的消息不会丢失推送事件。
- RabbitMQ 恢复后能够补发并正确更新会话排序。
- 重复事件不会产生重复消息或联系人。

### 4.7 消息内容和类型缺少服务端边界校验

#### 现状

`MessageSendDTO` 只校验接收人非空和内容非空，`messageType` 可由客户端传任意值，内容没有长度上限。

图片消息只保存 URL 字符串，未验证该 URL 是否来自可信上传服务。超长文本、伪造类型或外部跟踪图片都可能进入聊天记录。

#### 修改建议

1. 文本消息限制合理长度，例如 2000 个字符。
2. `messageType` 改为枚举，当前仅接受 `text` 和 `image`。
3. 文本经过标准化后再次检查空内容、XSS 和敏感词。
4. 图片消息只允许引用本站上传接口生成的对象标识或可信 URL。
5. 接口层限制请求体大小；上传层继续校验真实文件类型、大小和内容。

#### 验收标准

- 超长文本、未知消息类型、空白内容和非可信图片地址均被服务端拒绝。
- 前端错误提示能区分内容过长、类型不支持和上传失败。

## 5. P2：建议补齐的功能与体验

### 5.1 已读状态缺少实时回执

当前打开历史时会在服务端标记已读，但发送方不会实时收到“对方已读”事件，前端也没有可靠展示消息级已读状态。

建议：

- 以房间级 `lastReadMessageId` 表示读位置，避免逐条更新大量消息。
- 标记已读后向对方设备推送 `conversation_read` 事件。
- 前端只在最新一条自己的消息下展示“已送达/已读”。

### 5.2 举报证据关联不够严格

`reportUser` 接受客户端传入的目标用户和 `roomId`，没有验证举报者是否属于房间、目标用户是否是另一成员，也没有固定被举报消息快照。

建议：

- 举报消息时只接受 `messageId`，服务端从消息反查房间、被举报人和原始内容。
- 保存内容快照、消息类型、时间和附件证据，避免消息撤回或删除后证据丢失。
- 限制重复举报和短时间提交频率。

### 5.3 缺少消息发送状态与断线补偿

前端当前只有乐观成功或删除失败消息，没有“发送中、失败、重试、已送达”状态。WebSocket 断线恢复后也没有按最后消息 ID 补拉缺失消息。

建议：

- 消息前端状态使用 `sending/sent/failed/delivered/read`。
- WebSocket 重连后按每个打开会话的 `lastReceivedMessageId` 补拉。
- 应用切回前台时刷新会话列表和当前会话增量消息。

### 5.4 会话列表存在 N+1 查询

`listConversations` 为每个房间单独查询最后一条消息和未读数。会话数量增加后，单次请求会产生大量 SQL。

建议：

- 通过窗口函数、派生表或批量 SQL 一次查询每个房间最后消息。
- 批量统计未读数，或在 `contact` 中维护可校正的未读计数。
- 为 `private_chat(room_id, id)`、`private_chat(to_user_id, is_read, room_id)` 增加符合实际查询的组合索引。

### 5.5 会话生命周期未明确

目前有单侧清空消息，但没有“从会话列表删除/隐藏会话”和“收到新消息后重新出现”的明确规则。

建议：

- 增加单侧 `contact.hidden` 或归档状态，不删除双方房间。
- 用户删除会话后从自己的列表隐藏；收到新消息时自动恢复。
- 拉黑保留历史但禁止新消息；解除拉黑不自动恢复联系资格。

### 5.6 可选但常用的聊天能力

以下功能不是第一批安全修复的阻塞项，但达到完整社交产品体验时应评估：

- 消息复制
- 回复/引用消息
- 输入中状态
- 图片发送进度与失败重试
- 消息日期分段与未读分割线
- 离线通知或系统推送
- 多设备同步与登录设备管理
- 敏感操作审计和反骚扰限流

## 6. 测试缺口

### 当前状态

聊天模块目前只有以下测试文件：

- `AdminReportControllerTest`
- `BridgeServiceImplTest`

没有发现 `ChatServiceImpl`、`WebSocketServer`、`MsgSendConsumer` 或私聊控制器的自动化测试。

执行：

```powershell
mvn -pl finding-module-chat -am test
```

结果：用户模块 21 个测试通过，但聊天模块测试编译失败。失败位置为：

```text
BridgeServiceImplTest.java:236 找不到符号 never()
```

这通常是缺少 Mockito 静态导入：

```java
import static org.mockito.Mockito.never;
```

前端执行 `npm run build` 已通过，但构建成功不能覆盖上述权限和消息一致性问题。

### 必须新增的测试

1. 非成员不能读取、搜索、清空或修改其他房间。
2. 未批准申请不能创建会话或发送消息。
3. 双向拉黑后 REST 和 WebSocket 均不能发送消息。
4. 120 条消息的游标分页无重复、无遗漏且首次返回最新记录。
5. REST 发送返回真实消息 ID，重复 `clientMessageId` 不会重复落库。
6. 免打扰用户仍收到消息数据，但通知提示被抑制。
7. 并发创建会话不会产生重复房间或 `contact`。
8. RabbitMQ 重复投递时消费者保持幂等。
9. RabbitMQ 临时不可用后 Outbox 能够补发。
10. WebSocket 非法来源、失效 token 和客户端伪造聊天事件被拒绝。

## 7. 推荐修改顺序

### 第一阶段：立即封堵安全问题

1. 所有房间接口增加成员鉴权。
2. 禁止 WebSocket 直接转发客户端聊天内容。
3. 会话创建和消息发送接入聊天申请/会话资格规则。
4. 修复聊天模块测试编译，建立最小安全回归测试。

### 第二阶段：修复核心消息正确性

1. 改为游标分页并修复前端历史加载。
2. 发送接口返回真实消息，增加客户端幂等 ID。
3. 修正免打扰语义。
4. WebSocket 改为全局单例连接和可取消重连。
5. 添加 `contact(uid, room_id)` 唯一约束。

### 第三阶段：增强可靠性与完整体验

1. 增加事务 Outbox、发布确认、重试和死信队列。
2. 增加已读回执、断线补拉和多设备同步。
3. 完善举报证据、限流、会话隐藏与消息发送状态。
4. 优化会话列表 SQL 和索引。
