# 相亲（鹊桥）模块技术审查报告

> 审查方式：只读代码审查。本文不包含代码或数据库修改。

## 审查范围

- 推荐流与匹配偏好
- 聊天申请、审批、撤回、过期
- 信息互换与情感简历
- 拉黑、隐私、账号状态
- 会话创建、通知与行为事件
- 前端分页和交互
- 数据库约束与推荐行为记录

## 总体结论

模块已具备基础业务闭环：实名认证限制、双向拉黑拦截、申请冷却期、待处理申请唯一约束、审批条件更新、聊天房间成员校验，以及情感简历互换权限。

不过，推荐接口的匿名数据暴露、输入与资源保护、目标账号状态一致性、信息互换权限与并发控制仍有较高风险。建议完成全部 P1 项后，再进行大规模用户测试和上线压测。

## P1：高优先级问题

### P1-01 未登录用户可以获取真实推荐用户列表

**证据**

- `finding-server/finding-module-chat/src/main/java/com/finding/chat/controller/BridgeController.java:29-35`
- `finding-server/finding-module-chat/src/main/java/com/finding/chat/service/impl/BridgeServiceImpl.java:87-148`

`/api/v1/bridge/recommend` 不要求登录。`userId == null` 时服务仍查询正常、可搜索用户。尽管详细字段会被隐藏，返回体仍可能包含用户 ID、昵称、头像、学校、最近登录时间和距离。攻击者还能用不同的 `lat/lng` 请求结合距离进行位置侧信道推断。

**影响**

- 可匿名批量爬取用户目录。
- 校园、头像、活跃时间等资料可能泄露。
- 推荐接口可被用于位置区域推断。

**修复建议**

- 默认要求登录；未登录返回 `401`。
- 如必须有游客页，只返回静态示例，不查询真实用户。
- 对推荐接口增加用户、IP、设备维度限流。

**验收**

- 不带 Token 请求推荐接口返回 `401`。
- 游客无法取得真实用户 ID、学校、头像、活跃时间、距离。

### P1-02 推荐分页参数未校验，可触发异常和资源消耗

**证据**

- `BridgeController.java:30-33`
- `BridgeServiceImpl.java:184-187`

代码直接计算：

```java
int from = Math.min((page - 1) * size, total);
int to = Math.min(from + size, total);
List<Scored> paged = scored.subList(from, to);
```

`page`、`size` 没有范围校验。`page=0` 会产生负偏移；超大参数可造成整型溢出或大规模计算。

**修复建议**

- `page >= 1`，`size` 限制为 1-50 或 1-100。
- 用 `long` 计算偏移量。
- 非法参数返回参数错误，不能抛出 500。

**验收**

- `page=0`、负页码、`size<=0`、超大页码均返回明确参数错误。

### P1-03 推荐全量查询后在内存筛选和排序

**证据**

- `BridgeServiceImpl.java:120-148`
- `BridgeServiceImpl.java:151-199`

当前实现先查询全部候选用户，再在内存过滤年龄、距离、完整度和评分，最后排序、分页。

**影响**

- 用户量增长后，单请求 CPU、堆内存和数据库负载快速上升。
- 与匿名调用和曝光事件写入叠加时，可能造成服务不可用。

**修复建议**

- 将账号状态、搜索开关、性别、城市、认证和年龄范围下推数据库。
- 采用地理索引或候选半径查询。
- 使用候选池、分页评分和短时缓存，避免扫描全表。
- 对接口做限流和压测。

**验收**

- 使用 10 万、100 万用户数据压测 P95/P99 延迟、堆内存和数据库连接数。

### P1-04 聊天申请未检查目标账号状态

**证据**

- `BridgeServiceImpl.java:301-305`

这里只检查目标用户是否存在，没有判断其 `status == 1`。被封禁、注销或非正常账号仍可能收到申请；在自动通过模式下甚至可能被创建会话。

**修复建议**

- 申请前统一调用发现/申请权限策略。
- 检查目标账号状态、可搜索状态、拉黑状态和申请设置。
- 审批时再次检查双方账号状态。

**验收**

- 目标账号封禁、注销、隐藏时申请失败。
- 申请后目标账号被封禁，审批必须失败并关闭申请。

### P1-05 聊天申请没有完整复用发现权限规则

**证据**

- `BridgeServiceImpl.java:296-313`
- `finding-server/finding-module-user/src/main/java/com/finding/user/service/impl/UserRelationshipServiceImpl.java:90-96`

推荐流程会考虑账号状态和 `searchable`，但聊天申请只检查用户存在、拉黑和 `friendAddMode`。因此攻击者可以通过手工构造用户 ID 向不可搜索用户申请。

**修复建议**

- 建立单一的服务层权限入口，例如 `canApplyChat`。
- 统一校验目标状态、可发现性、拉黑和申请模式。
- 为“不可发现”和“不可申请”提供明确错误码。

### P1-06 信息互换申请缺少拉黑、账号状态、关系和频率限制

**证据**

- `finding-server/finding-module-chat/src/main/java/com/finding/chat/controller/InfoShareController.java:21-27`
- `finding-server/finding-module-chat/src/main/java/com/finding/chat/service/impl/InfoShareServiceImpl.java:34-45`

信息互换仅检查“非本人、发起方实名认证、目标存在”，没有检查双向拉黑、目标账号状态、可发现性、是否已有聊天关系或请求频率。

**影响**

- 可绕过聊天申请关系直接向任意用户发互换请求。
- 被拉黑用户仍可能发起互换请求。
- 可批量制造站内信和 WebSocket 通知骚扰。

**修复建议**

- 增加双向拉黑、账号状态和可发现性判断。
- 明确业务规则：是否必须先通过聊天申请才允许互换。
- 对拒绝后重试增加冷却期。
- 增加用户、目标、IP、设备维度限流。
- 拉黑事件发生时取消双方待处理的互换申请。

### P1-07 信息互换审批不是条件更新，存在并发重复处理

**证据**

- `InfoShareServiceImpl.java:83-107`

流程先查询 `pending` 状态，再 `updateById`，没有在更新条件中约束 `status=0`。并发的通过/拒绝请求都可能读取到待处理状态并分别成功写入，造成最终状态不确定或重复通知。

**修复建议**

- 使用 `WHERE id=? AND to_user_id=? AND status=0` 的条件更新。
- 仅在更新行数为 1 时发送通知。
- 对外部通知使用事务提交后的 Outbox 机制。

**验收**

- 20 个并发同意/拒绝请求只能有一个成功。
- 只产生一条最终状态通知。

### P1-08 推荐曝光事件可被无限刷写

**证据**

- `BridgeServiceImpl.java:193-197`
- `BridgeServiceImpl.java:566-571`
- `deploy/init.sql:722-730`

每次推荐请求会为当前页每位用户逐条插入一条 `expose` 事件，没有去重、限流、批量写入或保留策略。

**影响**

- 重复刷新即可持续放大数据库写入。
- 事件表膨胀，后台统计变慢。
- 推荐接口形成读、算、写三重放大。

**修复建议**

- 对同一用户、目标、事件类型在时间窗口内去重，例如 24 小时。
- 使用批量插入或聚合计数表。
- 增加历史事件归档、清理策略和必要索引。

### P1-09 批准会话的外部副作用需要可靠投递边界

**证据**

- `BridgeServiceImpl.java:450-453`
- `BridgeServiceImpl.java:576-618`

批准操作在一个事务内创建会话、系统消息、联系人、关注关系并发送通知。数据库事务能保护内部写入，但 `messageService.notify`、WebSocket 或后续异步依赖是否能和事务保持一致仍不确定。

**修复建议**

- 事务内只写申请状态、会话、联系人和 Outbox 事件。
- 由异步任务可靠投递站内信和 WebSocket。
- 以 `applyId` 作为幂等键，避免重试产生重复消息。
- 增加失败补偿和管理员修复入口。

## P2：中优先级问题

### P2-01 匹配偏好缺少完整边界校验

**证据**

- `BridgeController.java:101-107`
- `BridgeServiceImpl.java:516-545`

已校验性别、目标类型、完整度、年龄大小关系，但未校验：

- `maxDistanceKm` 非负及上限
- `onlyVerified` 只能为 0/1
- 年龄合理上限
- `preferCity` 长度、空白清理和格式
- 空请求体

**修复建议**

- 使用专用 DTO，不直接接收实体。
- 添加 Bean Validation 和服务层二次校验。
- 城市统一 `trim`，限制长度和格式。

### P2-02 推荐坐标缺少范围校验

**证据**

- `BridgeController.java:30-33`
- `BridgeServiceImpl.java:260-280`

`lat/lng` 未验证纬度 `[-90, 90]`、经度 `[-180, 180]`、NaN 和无穷值。

**修复建议**

- 在 Controller 和服务层双重校验。
- 非法坐标返回参数错误或降级为无定位推荐。
- 避免对普通用户暴露过精确距离。

### P2-03 推荐结果存在 N+1 查询

**证据**

- `BridgeServiceImpl.java:671-695`

`toFeedVO` 对页面中每个候选人单独查询申请状态。每页 50 人时，会额外增加约 50 次查询。

**修复建议**

- 批量查询申请状态并在内存用 `Set` 判断。
- 使用聚合查询，避免逐候选人查询。

### P2-04 情感简历保存缺少字段级校验

**证据**

- `finding-server/finding-module-user/src/main/java/com/finding/user/controller/ResumeController.java:31-39`
- `finding-server/finding-module-user/src/main/java/com/finding/user/service/impl/UserResumeServiceImpl.java:37-50`
- `finding-server/finding-module-user/src/main/java/com/finding/user/dto/UserResumeDTO.java`

当前只做敏感词过滤，缺少文本长度、年龄生日一致性、身高体重范围、图片数量与 URL 格式、枚举字段等校验。

**修复建议**

- 为 DTO 添加字段级校验。
- 生日作为年龄的唯一来源。
- 限制相册数量、URL 长度、协议和文本长度。

### P2-05 情感简历更新缺少并发保护确认

**证据**

- `UserResumeServiceImpl.java:41-49`

该逻辑先查询、后插入或更新。若 `user_resume.user_id` 没有唯一约束，并发首次保存可能出现重复记录。

**修复建议**

- 确认 `user_resume.user_id` 具有唯一索引。
- 插入冲突时重新查询并更新。
- 可增加版本号或更新时间乐观锁。

### P2-06 前端申请列表只加载前 50 条

**证据**

- `finding-web/src/pages/Bridge/SendApplyList.tsx`
- `finding-web/src/pages/Bridge/ReceiveApplyList.tsx`

前端固定请求第一页、50 条记录，然后在客户端按状态过滤。超过 50 条后，历史申请会被遗漏。

**修复建议**

- 使用服务端分页和状态筛选。
- 增加加载更多或分页。
- 展示过期、撤回、拒绝等完整状态。

### P2-07 前端错误提示未保留服务端业务原因

**证据**

- `SendApplyList.tsx`
- `ReceiveApplyList.tsx`

多个失败场景统一显示“操作失败”“撤回失败”，丢失冷却、拉黑、过期、重复申请等具体业务信息。

**修复建议**

- 统一按错误码映射用户文案。
- 并发处理失败后刷新申请列表。
- 对冷却、拉黑、过期提供明确提示。

### P2-08 聊天页路由携带的用户资料不能作为可信数据源

**证据**

- `finding-web/src/pages/Bridge/SendApplyList.tsx`
- `finding-web/src/pages/Bridge/ReceiveApplyList.tsx`

已通过申请后，前端通过 query 参数拼接 `userId`、昵称和头像进入聊天页。当前后端有房间成员校验，这一层保护是有效的，但页面资料仍应以后端会话接口为准。

**修复建议**

- 聊天页加载时向后端查询会话。
- 不信任 URL 中的昵称、头像和房间信息。
- 会话不存在或无权限时回到申请页并提示原因。

## 已确认的现有防护

1. 聊天申请会执行 `UserWriteGuard`。
2. 聊天和信息互换的发起方需要实名认证。
3. 聊天申请存在小时级频率限制。
4. 禁止向自己发送申请。
5. 聊天申请会检查双向拉黑。
6. 聊天申请备注经过敏感词过滤。
7. 聊天申请在拒绝或撤回后有 7 天冷却期。
8. `chat_apply.pending_key` 防止同方向重复待处理申请。
9. 聊天申请审批和撤回使用 `status=PENDING` 条件更新。
10. 拉黑事件会取消双方待处理聊天申请。
11. 聊天房间使用 `room_key` 唯一约束保证幂等。
12. 聊天会话访问会校验当前用户是否为房间成员。
13. 情感简历在未互换信息时不返回正文。
14. 推荐结果会按资料可见性隐藏部分详细字段。

## 建议修复顺序

### 第一阶段：立即处理

1. 禁止未登录用户读取真实推荐数据。
2. 增加推荐分页、坐标和请求频率限制。
3. 聊天申请统一校验目标账号状态与发现权限。
4. 信息互换增加拉黑、账号状态、关系和频率限制。
5. 信息互换审批改为条件更新。
6. 推荐曝光事件做去重和限流。

### 第二阶段：稳定性和一致性

1. 将推荐全量内存计算改为候选池或分层数据库查询。
2. 引入 Outbox 处理审批后的通知与系统消息。
3. 消除推荐列表中的 N+1 查询。
4. 为情感简历增加字段校验和并发保护。
5. 为申请记录补齐服务端分页和状态筛选。

### 第三阶段：产品完善

1. 明确聊天申请与信息互换的业务先后关系。
2. 补齐过期、撤回、拒绝、冷却的前端状态展示。
3. 明确举报、拉黑、取消关注后的会话与资料互换联动规则。
4. 增加异常申请审计、数据修复和运营风控能力。
5. 建立推荐解释、隐私保护、事件保留与删除策略。

## 必须补充的测试

### 权限与隐私

- 未登录访问推荐接口。
- `searchable=0` 用户被直接指定 ID 申请。
- `profileVisible=2` 时未互换信息查看简历。
- 双向拉黑后推荐、聊天申请、信息互换。
- 被封禁账号存在历史申请时的继续操作。

### 并发

- 同一聊天申请同时通过和拒绝。
- 同一用户并发发送相同申请。
- 同一用户并发创建信息互换申请。
- 两个申请同时批准创建会话。
- 通知服务失败后的审批重试。

### 参数与异常

- `page=0`、负数页码、极大页码。
- `size=0`、负数和超大值。
- 非法纬度、经度、NaN。
- 负年龄、超大年龄、年龄范围反转。
- 超长城市、备注和简历字段。
- 空请求体和缺少必填字段。

### 性能

- 10 万以上用户的推荐请求。
- 连续刷新推荐页面。
- 多用户并发曝光。
- 大量申请记录下的收发列表。
- 推荐事件表增长后的统计查询。
