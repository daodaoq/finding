# 发布活动与寻找搭子功能审查及修改建议

## 1. 审查范围

本次审查覆盖“发布活动、寻找搭子”的完整业务链路：

- 搭子活动创建、编辑、审核、取消和关闭
- 活动列表、全局搜索、分类、时间、地点和距离筛选
- 报名、审批、拒绝、退出、候补和自动补位
- 活动人数、并发名额与数据库约束
- 匿名发布、拉黑、举报和活动地点隐私
- 发起人、报名者的管理页面与通知
- 管理后台审核、下架和删除
- 前后端状态一致性与现有测试

主要涉及文件：

- `finding-server/finding-module-mate/src/main/java/com/finding/mate/service/impl/MateServiceImpl.java`

## 2. 总体结论

当前模块已经具备活动发布、审核、报名审批、候补、退出补位、人数统计、拉黑拦截、举报、通知和个人活动列表等基础能力，业务骨架比单纯的展示页面完整。

但现状仍有三类上线阻塞问题：

1. 编辑已发布活动可以绕过内容审核，而且清洗后的内容没有真正保存。
2. 匿名活动仍在 API 中返回发起人 `userId`，匿名身份可以被直接还原。
3. 全局搜索没有过滤审核、取消、关闭和过期状态，会重新暴露本应隐藏的活动。

此外，活动状态机、取消后的报名状态、人数并发、表单校验、前端管理入口和筛选功能都没有形成完整闭环。建议按本文优先级修改。

## 3. P0：必须立即修复的安全与审核问题

### 3.1 编辑活动可以绕过内容审核 ✅ 已完成

#### 现状

创建活动时，`createInvitation` 会调用 `classifyReview`，命中“送审”规则的内容会设置 `reviewStatus = 1`，命中“拦截”规则则拒绝发布。

编辑活动时存在两个问题：

1. 代码先把原始 `dto.title`、`dto.description` 写入实体，再清洗 DTO，因此最终保存的仍是清洗前的原始内容。
2. 编辑只调用 `assertClean`，没有重新执行“拦截/送审”分类，也没有将已发布活动重新置为待审核。

因此，用户可以先发布正常内容，再通过编辑加入需要人工审核的敏感内容，而活动仍保持公开状态。

#### 影响

- 内容审核可被稳定绕过。
- 已公开活动可能出现违法、骚扰、引流或不适合校园场景的内容。
- 管理员审核记录与用户当前看到的内容不一致。

#### 修改建议

1. 抽取统一的 `prepareMateContent` 或内容审核服务，创建和编辑必须走同一套 XSS 清洗、敏感词分类和字段标准化。
2. 先生成清洗后的局部变量，再写入实体，禁止先赋原始值后修改 DTO。
3. 标题、描述、地点、分类、时间、人数任一关键字段被修改时，重新计算审核状态。
4. 命中送审规则后，将活动置为 `PENDING_REVIEW` 并立即从公开列表和搜索中隐藏。
5. 保留“修改前版本”和“待审版本”，避免编辑送审期间公开内容突然消失；第一阶段也可以采用简单方案：编辑后整体暂时不可见。
6. 管理后台编辑同样需要 DTO 校验、清洗和审计，不能直接使用 `Map<String, Object>` 任意覆盖字段。

#### 验收标准

- 已发布活动编辑为需送审内容后，立即从公开列表和搜索消失。
- 编辑命中拦截词时数据库内容不变。
- 数据库保存的是清洗后的内容。
- 创建和编辑使用同一组内容审核测试用例。

### 3.2 匿名活动泄露发起人 ID ✅ 已完成

#### 现状

`toVO` 对匿名活动不设置 `author`，但仍无条件执行：

```java
vo.setUserId(m.getUserId());
```

前端或任意 API 调用者可以读取 `userId`，再访问用户资料接口，从而还原匿名发布者。当前匿名仅隐藏了作者卡片，不是真正的身份保护。

#### 影响

- 匿名功能承诺与实际行为不一致。
- 在校园小范围社交环境中，可能造成骚扰、报复或隐私泄露。

#### 修改建议

1. 公共 `MateVO` 在匿名活动中不返回发起人 ID 和作者资料。
2. 增加面向本人和管理员的管理 VO，只有活动本人和管理员可以看到真实 `creatorId`。
3. 报名和举报时由服务端从活动记录解析发起人，不依赖客户端提交作者 ID。
4. 活动参与者是否能在审批通过后看到发起人身份，需要明确产品规则。推荐“报名通过后可见”，并由服务端根据参与状态投影。
5. 匿名活动的精确地点也应考虑分级展示：公开列表展示校区或区域，报名通过后展示具体集合点。

#### 验收标准

- 未报名访客、待审批用户无法从任何活动 API 获得匿名发起人的 ID。
- 发起人本人和管理员仍可管理、审核和举报追溯。
- 通过报名后的身份与地点可见性符合统一规则。

### 3.3 全局搜索绕过活动审核与状态过滤 ✅ 已完成

#### 现状

搭子列表接口只查询：

- `status = ACTIVE`
- `reviewStatus = PUBLISHED`
- 活动时间未过期

但 `SearchController` 的搭子搜索只按标题模糊匹配，没有过滤：

- 待审核活动
- 审核拒绝活动
- 已取消活动
- 已关闭活动
- 已过期活动
- 与当前用户双向拉黑的发起人

用户可以通过全局搜索重新发现不应公开的活动。

#### 修改建议

1. 不要在全局搜索控制器中直接查询 `MateInvitationMapper`。
2. 抽取统一的“公开活动查询条件”，由搭子列表和全局搜索共同复用。
3. 公开查询必须同时检查活动状态、审核状态、活动时间、发起人账号状态和双向拉黑关系。
4. 匿名活动搜索结果使用匿名投影，不返回作者 ID。
5. 为“公开可见性”添加集成测试，避免以后新增入口再次绕过。

#### 验收标准

- 同一活动在列表和全局搜索中的可见性完全一致。
- 待审、拒绝、取消、关闭、过期及被拉黑发起人的活动不会出现在搜索结果中。

## 4. P1：上线前必须修复的业务正确性问题

### 4.1 创建与编辑参数校验不足

#### 现状

`MateCreateDTO` 没有验证以下约束：

- 活动时间必须晚于当前时间，并保留合理发布提前量。
- `category` 必须属于系统支持的分类枚举。
- `maxParticipants` 必须在合理范围内，且至少包含发起人和一名参与者。
- `isAnonymous` 只能是 `0/1`。
- 经纬度范围是否合法，以及经纬度是否必须同时存在。
- 地点长度与格式。

前后端还存在直接冲突：后端要求 `location` 非空，前端页面却把地点标为选填，并在空值时发送 `undefined`。用户按界面提示不填地点会发布失败，但只看到笼统的“发布失败”。

#### 修改建议

1. 使用 Bean Validation 和服务层规则共同校验。
2. 推荐限制：人数 `2..50`、标题 `1..100`、描述最多 2000、地点最多 200。
3. 活动时间至少晚于当前时间 30 分钟，是否限制最长可预约时间由产品决定。
4. 分类使用枚举校验，不接受任意字符串。
5. 明确地点是否必填，并同步修改前端文案和后端 DTO。
6. 编辑时额外检查新人数不能小于已确认人数。
7. 前端显示服务端具体错误，不要把所有异常吞成“发布失败”。

#### 验收标准

- 过去时间、非法分类、人数 0/1/超上限、非法匿名值和单边经纬度均被拒绝。
- 前后端对地点是否必填的规则一致。
- 所有非法请求均不会写入数据库。

### 4.2 活动状态机不完整

#### 现状

活动落库状态只有：

- `CANCELLED`
- `ACTIVE`
- `CLOSED`

“满员”和“过期”由字段临时计算，但没有统一状态迁移。普通用户端只有取消接口，没有明确的关闭、重新开放或完成接口。代码中也没有定时任务将过期活动收敛到结束状态。

结果是：

- `CLOSED` 状态主要依赖管理员任意设置，发起人无法正常完成活动。
- 不同查询各自解释“进行中/已结束”，容易产生不一致。
- 已过期活动的待审批和候补申请长期保持原状态。

#### 建议状态模型

活动状态：

```text
DRAFT/PENDING_REVIEW -> OPEN -> CLOSED | CANCELLED | EXPIRED
```

其中 `FULL` 建议作为派生状态，不单独落库；审核状态可以独立于业务状态，但公开活动必须同时满足 `OPEN + PUBLISHED + 未过期`。

#### 修改建议

1. 明确发起人可执行的关闭和取消操作：关闭表示停止新增报名但活动仍有效，取消表示活动不再举行。
2. 增加定时任务或查询时幂等收敛，将过期活动置为 `EXPIRED`，并处理未完成报名。
3. 所有接口通过状态机方法迁移，禁止控制器直接写任意整数状态。
4. 管理后台状态接口改为明确命令，例如 `close/cancel/restore`，并限制合法迁移。

#### 验收标准

- 每个状态下允许的报名、审批、编辑、退出和取消动作有确定结果。
- 过期活动的待审批和候补申请被自动结束并通知用户。
- 列表、详情、我的活动和全局搜索对状态理解一致。

### 4.3 取消活动后报名记录没有结束

#### 现状

取消活动只修改 `mate_invitation.status` 并发送通知，没有更新参与记录。已通过、待审批和候补用户仍保留原报名状态。

`getMyJoinedInvitations` 的“已结束”筛选只识别 `status = CLOSED` 或时间过期，不识别未来时间的 `CANCELLED` 活动，因此已取消活动可能既不在“进行中”，也不在“已结束”。

#### 修改建议

1. 取消活动时在同一事务中将 `PENDING`、`WAITLISTED`、`ACCEPTED` 迁移为明确的终态，例如 `CANCELLED_BY_CREATOR`。
2. 不要复用参与者主动退出的 `CANCELLED` 含义；区分“本人退出”和“活动取消”。
3. 已结束筛选包含关闭、取消和过期三类状态。
4. 通知文案区分活动取消、申请失效和成员退出。
5. 保留历史记录用于审计，不物理删除报名关系。

#### 验收标准

- 取消后所有未完成申请都有明确终态。
- 参与者在“已结束/已取消”活动列表中仍能找到历史记录和取消原因。
- 取消操作和批量报名状态更新保持事务一致。

### 4.4 候补补位存在计数与参与状态不一致风险

#### 现状

`promoteWaitlist` 先把候补者更新为 `ACCEPTED`，再尝试增加 `currentParticipants`，但没有检查人数更新结果。

如果人数更新因为并发、人数上限被修改或其他条件失败，候补者仍会保持“已通过”，且还会收到补位成功通知，但人数没有增加。

#### 修改建议

1. 将“占用名额”作为第一步原子条件更新，成功后再迁移候补状态。
2. 或对活动行使用 `SELECT ... FOR UPDATE`，在一个事务内锁定活动、选择候补、更新状态和人数。
3. 任一步骤失败必须抛异常回滚，不能发送成功通知。
4. 通知使用事务后事件，避免数据库回滚但通知已发出。
5. 添加真实数据库并发测试，Mockito 单元测试无法证明锁和原子 SQL 正确。

#### 验收标准

- 多人同时退出、审批和补位时，`currentParticipants` 始终等于发起人加已确认参与者数量。
- 已确认人数永远不超过 `maxParticipants`。
- 补位通知只在状态和人数都提交成功后发送。

### 4.5 编辑活动缺少业务限制和变更通知

#### 现状

发起人可编辑任意状态和任意阶段的活动，并可以：

- 把最大人数改到低于当前已确认人数。
- 在已有参与者后大幅修改时间、地点、类型和活动内容。
- 编辑已取消、关闭或过期活动。
- 修改后不通知已通过、待审批和候补用户。

编辑接口还没有调用 `userWriteGuard.checkWritable`，被冻结或受限用户可能仍能修改活动。

#### 修改建议

1. 编辑操作接入账号写权限校验。
2. 仅允许编辑 `OPEN` 且未过期活动；取消/关闭后不可直接编辑。
3. 最大人数不得小于当前已确认人数。
4. 已有报名后修改时间、地点和核心内容，需要二次确认并通知所有相关用户。
5. 对重大变更保存变更摘要，前端显示“活动信息已更新”。
6. 审核拒绝后的活动允许修改并重新提交审核，但不能直接恢复公开。

#### 验收标准

- 受限账号和终态活动不能编辑。
- 已确认 5 人时不能把上限改为 4。
- 时间或地点变更后，所有相关用户收到一次通知。

### 4.6 报名状态不允许合理的重新申请

#### 现状

数据库对 `(invitation_id, user_id)` 建立唯一约束，服务层只要发现任何历史报名记录就永久拒绝再次报名。

这意味着用户被拒绝或主动退出后，即使活动信息发生变化，也永远不能再次申请。当前前端也直接显示“已申请过，无法重复加入”。

#### 修改建议

1. 先明确规则。推荐：待审批、候补和已通过不可重复；被拒绝后设置冷却期；本人退出后是否允许重新申请由活动状态和退出次数决定。
2. 保留单行报名记录时，可在允许重试时重置状态并增加 `applyCount`、`lastAppliedAt`。
3. 若需要完整审计，可拆分“参与关系”和“申请尝试记录”。
4. 防骚扰规则应通过冷却期和频率限制实现，而不是永久禁止所有再次申请。

#### 验收标准

- 各终态是否允许重试有明确规则和错误提示。
- 重试不会绕过冷却期，也不会丢失历史审批记录。

### 4.7 报名和退出的前端人数显示错误

#### 现状

列表页报名成功后，前端立即执行：

```ts
currentParticipants + 1
```

但服务端新报名只进入 `PENDING` 或 `WAITLISTED`，并没有占用确认名额。界面会把待审批用户错误计入已参与人数。

详情页退出时也直接减 1，虽然当前按钮主要对已通过用户展示，但客户端不应自行推导服务端计数。

#### 修改建议

1. 报名、审批、退出接口返回最新活动摘要或重新拉取详情。
2. 前端报名后只更新 `myApplicationStatus`，不自行修改 `currentParticipants`。
3. 人数必须以服务端已确认计数为准。
4. 明确 UI 同时展示“已确认人数”和“待处理/候补人数”，避免概念混淆。

#### 验收标准

- 新报名待审批时确认人数不变。
- 审批通过、退出和候补补位后数字与数据库一致。

### 4.8 满员活动的候补入口在不同页面不一致

#### 现状

详情页满员时显示“加入候补”，服务端也支持创建 `WAITLISTED` 报名。

但 `MateCard` 在 `mate.isFull` 时完全不显示报名按钮，用户只能先进入详情页才能发现候补功能。卡片还可能把“满员但未报名”的用户显示成“已加入”。

#### 修改建议

1. 卡片根据 `myApplicationStatus` 展示准确状态。
2. 满员且未报名时显示“加入候补”，而不是“已加入”。
3. 区分待审批、已通过、候补、已拒绝、本人退出和活动取消。
4. 所有列表统一复用一个状态展示函数或组件。

#### 验收标准

- 同一用户在首页、搭子列表、详情和我的页面看到的报名状态一致。
- 未报名的满员活动不会显示“已加入”。

## 5. P2：必须补齐的产品与管理能力

### 5.1 活动筛选控件大多是静态装饰

#### 现状

搭子页显示“匿名匹配、类型、时间、地点、搜索”，但只有分类网格真正影响请求。

`MateQueryDTO` 定义了城市、经纬度和半径，服务层只计算距离，没有应用城市或半径过滤，也没有按距离排序。页面文案写“按距离/时间排序”，实际后端只按活动时间升序。

#### 修改建议

1. 把时间范围、地点/校区、距离半径、是否匿名、是否有空位做成真实筛选参数。
2. 服务端必须执行筛选，不能只在前端过滤当前页。
3. 明确排序方式：最近时间、最近距离、最新发布。
4. 搜索输入接入标题和描述关键词。
5. 无定位权限时隐藏距离排序或提示选择校区。

### 5.2 发起人缺少编辑、取消和关闭入口

后端存在更新和取消接口，但 `mateApi` 没有暴露对应方法，`MyInvitations` 和详情页也没有编辑、取消或关闭操作。普通发起人实际上无法完成活动管理闭环。

建议：

- 在“我发布的活动”和详情页增加编辑、停止报名、取消活动入口。
- 危险操作使用确认弹窗，并说明对报名者的影响。
- 待审核/审核拒绝活动提供“修改并重新提交”。
- 显示待处理申请数量和活动变更状态。

### 5.3 报名者缺少完整申请记录入口

后端已有 `/mates/my-applications`，前端 API 也已声明，但没有页面消费它。用户只能在“我加入的搭子”中看到已通过记录，待审批、候补和被拒绝记录缺少统一入口。

建议新增“我的报名”页面，按待处理、候补、已通过、已拒绝、已退出、活动取消分类，并提供撤回申请、退出活动和查看原因等操作。

### 5.4 报名申请不能填写留言

服务端支持 `message`，但首页、列表和详情都直接调用 `mateApi.join(id)`，没有给用户填写自我介绍、时间确认或备注的界面。

建议在申请前打开简洁弹层，允许填写最多 200 至 500 字留言，并明确将向发起人展示哪些资料。

### 5.5 缺少参与者名单和活动后的联系通道

当前只有发起人能查看申请人，已通过成员无法看到其他确认成员，也没有活动群聊或受控联系方式交换。

需要结合隐私规则决定：

- 已通过成员是否互相可见。
- 是否自动建立活动群聊。
- 具体地点和联系方式何时解锁。
- 发起人取消或成员退出后如何退出群聊。

推荐在报名通过后创建活动群或活动讨论区，不要自动把所有成员互相关注。

### 5.6 拉黑后的既有报名缺少处理规则

当前拉黑只阻止新报名和审批，已经通过、待审批或候补的关系不会自动变化。

建议：

- 任一方拉黑后，双方之间的待审批和候补申请自动失效。
- 已通过关系是否取消需要明确，安全优先时建议取消并释放名额。
- 取消后保留审计记录并通知必要一方，但不暴露是谁执行了拉黑。

### 5.7 管理后台操作缺少严格校验

管理后台目前可以写任意状态整数、编辑任意人数和时间，并支持物理删除活动及其参与记录。

建议：

- 管理端使用强类型 DTO 和枚举校验。
- 审核只允许待审核状态处理，使用条件更新防止重复审批。
- 下架与取消通知相关用户，并记录完整审计日志。
- 删除改为软删除；举报、审核和参与记录不得被物理清除。
- 审核拒绝必须填写原因，通过和拒绝均通知作者。

### 5.8 匿名与精确地点的隐私策略未完成

当前活动公开返回经纬度和地点。对于匿名活动、拼车或线下见面场景，精确集合地点不宜在审批前对所有人公开。

建议将地点拆为：

- 公开区域：学校、校区、商圈或大致范围。
- 精确集合点：仅发起人和已通过成员可见。
- 经纬度：公共接口返回模糊化坐标或只返回计算后的距离。

### 5.9 分类来源重复且仍返回 Emoji

分类同时存在于前端常量、后端枚举和控制器硬编码列表，容易出现名称或图标不一致。分类接口仍直接返回 Emoji 图标，与项目当前统一使用线性图标的规范冲突。

建议由后端只返回稳定分类代码和名称，前端通过统一 `AppIcon` 映射图标；或者由一个共享配置源生成两端类型。

## 6. 数据模型与查询建议

### 6.1 参与人数应可校验和修复

`currentParticipants` 是冗余计数字段，读取快但可能与参与记录不一致。

建议：

1. 明确它包含发起人，因此最小值为 1。
2. 所有增减只通过一个领域服务执行。
3. 增加定期校验任务，根据 `ACCEPTED` 记录重新计算异常活动。
4. 管理后台提供只读的一致性告警，不允许手工随意改计数。

### 6.2 增加必要索引

根据实际查询建议评估：

- `mate_invitation(status, review_status, activity_time)`
- `mate_invitation(category, status, review_status, activity_time)`
- `mate_participant(invitation_id, status, created_at)`
- `mate_participant(user_id, status, created_at)`

现有 `(invitation_id, user_id)` 唯一约束可保留，但需配合重新申请的数据模型。

### 6.3 避免内存分页

`getMyJoinedInvitations` 先加载用户全部已通过记录和全部活动，再在内存中筛选、排序和分页。数据增长后性能和页码稳定性都会下降。

建议使用 JOIN 查询或先分页活动 ID，在数据库中执行状态、时间和排序条件。
